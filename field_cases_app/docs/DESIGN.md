# وثيقة التصميم — تطبيق الحالات الميدانية (Field Cases)

> المرجع الأساسي للمتطلبات: [`REQUIREMENTS.md`](REQUIREMENTS.md).
> هذه الوثيقة تغطي البنود 1–18 المطلوبة قبل البرمجة، وتُحدَّث مع كل مرحلة.
> أي تغيير على قاعدة البيانات أو صيغة الحزمة يُوثَّق هنا مع السبب.

## 1) تحليل المتطلبات

### 1.1 المتطلبات الوظيفية (مختصرة ومجمّعة)

| المجموعة | المتطلبات |
|---|---|
| الإدخال | نموذج ذكي متدرّج حسب نوع الحالة، حقول عامة + حقول ديناميكية لكل نوع، إحداثيات GPS، صور من الكاميرا/المعرض |
| الصياغة | توليد نص الحالة آليًا من قوالب قابلة للتعديل لكل نوع، مع إمكانية تعديل النص النهائي يدويًا |
| السجل | قائمة الحالات السابقة (الأحدث أولًا، مجمّعة باليوم)، بحث، فلاتر، حالات السجل (Status) |
| المشاركة | Share Sheet للنظام (WhatsApp أو غيره باختيار المستخدم)، نسخ النص، مشاركة الصور |
| التصدير | حالة واحدة / تحديد يدوي / كل غير المصدّر / (مستقبلًا) فترة زمنية — في حزمة `.casepkg` |
| المشرف | استيراد، فحص قبل الإدخال، صندوق وارد، مراجعة واعتماد/رفض، منع التكرار، مقارنة الإصدارات، إحصاءات حسب الجهة والنوع |
| الحماية | قفل التطبيق (بصمة/وجه + PIN)، تشفير الحزم والنسخ الاحتياطية، تخزين الأسرار في Keychain/Keystore |
| السلامة | Transactions، Soft Delete + المحذوفات، Audit Log |
| النسخ الاحتياطي | نسخة مشفرة يختار المستخدم مكان حفظها، واستعادة مع تحذيرات |

### 1.2 المتطلبات غير الوظيفية

- **Offline 100%**: لا يوجد في الكود أي عميل HTTP ولا أي SDK سحابي/تحليلي. سيُضاف فحص آلي (CI/اختبار) يرفض أي حزمة تعتمد على `http`/`dio`/`firebase_*`.
- **الخصوصية**: البيانات لا تغادر الجهاز إلا بفعل صريح من المستخدم (مشاركة/تصدير/نسخة احتياطية).
- **الأداء**: آلاف الحالات والصور → Pagination (Keyset)، Indexes، Thumbnails، تحميل كسول.
- **قابلية الصيانة**: طبقات منفصلة، كل خدمة قابلة للاختبار بدون جهاز.
- **التوافق للخلف**: أي إصدار معتمد من صيغة `.casepkg` يبقى قابلًا للاستيراد في الإصدارات اللاحقة.
- **الواجهة**: عربية بالكامل، RTL، أزرار كبيرة، استخدام بيد واحدة (الأزرار الرئيسية أسفل الشاشة).

### 1.3 افتراضات وقرارات تحتاج تأكيدك

1. **الدور (Role) ليس حماية أمنية بذاته**: أي شخص يملك التطبيق يستطيع نظريًا تفعيل وضع المشرف. الحماية الحقيقية تأتي من **التشفير بالمفتاح العام** (البند 13): الحزمة لا يفتحها إلا جهاز المشرف الذي يملك المفتاح الخاص. تفعيل وضع المشرف محمي بـ PIN إضافي.
2. **الحالة المستوردة لا يعدّلها المشرف مباشرة** بل يعتمدها أو يرفضها؛ التعديل عليها ينشئ مراجعة (revision) جديدة مصدرها المشرف (موثّق في Audit Log).
3. **خط العرض**: يُستخدم خط النظام في البداية، ويمكن تضمين خط عربي (مثل Cairo) كملف داخل التطبيق لاحقًا — دون أي تحميل من الإنترنت.
4. **فتح الإحداثيات على الخريطة** يتم بتسليم الإحداثية لتطبيق الخرائط المثبت عبر رابط `geo:`/Apple Maps؛ التطبيق نفسه لا يتصل بالإنترنت.

## 2) المعمارية المقترحة (Architecture)

معمارية **Clean Architecture مبسّطة** بثلاث طبقات لكل ميزة (Feature-first):

```
┌──────────────────────────────────────────────┐
│ Presentation  (Screens, Widgets, Controllers) │  Flutter + Riverpod
├──────────────────────────────────────────────┤
│ Domain        (Entities, Services, Rules)     │  Dart خالص — قابل للاختبار
│   CaseStatusMachine, TemplateEngine,          │
│   DuplicateDetector, PackageBuilder ...       │
├──────────────────────────────────────────────┤
│ Data          (Repositories, DAOs, Files)     │  Drift/SQLite + File System
│   + Platform adapters (GPS, Camera, Share,    │
│     SecureStorage, Biometrics, FilePicker)    │
└──────────────────────────────────────────────┘
```

- **Riverpod** لإدارة الحالة وحقن الاعتماديات (يسهل استبدال أي خدمة بـ Fake في الاختبارات).
- **Repository Pattern**: الواجهة لا تعرف SQLite؛ تتعامل مع Repositories.
- كل تكامل مع النظام (GPS، الكاميرا، المشاركة...) خلف **Adapter** بواجهة مجردة، لتبقى المنطقيات قابلة للاختبار.

## 5) تصميم قاعدة البيانات

- قاعدة واحدة `field_cases.db` داخل مجلد التطبيق الخاص (Application Support)، مستقلة لكل جهاز.
- كل المفاتيح الأساسية للبيانات القابلة للنقل = **UUID نصي** (لا تتصادم بين الأجهزة).
- القوائم (أنواع الحالات، المحافظات...) في جدول عام `lookup_items` لتكون قابلة للتعديل.
- الحقول الخاصة بكل نوع حالة تُعرَّف في `case_type_fields` وقيمها تُحفظ في عمود JSON `extra_fields_json` داخل الحالة → إضافة حقل جديد لنوع لا تحتاج Migration.
- التواريخ تُخزَّن **UTC بصيغة ISO-8601** (للفرز والنقل بين الأجهزة) وتُعرض بالتوقيت المحلي.

**Indexes**: `(deleted_at, occurred_at DESC)`, `status`, `case_type_id`, `governorate_id`, `review_state`, `source_batch_id`, `display_code`.
جدول **FTS5** `cases_fts(display_code, location_text, location_description, case_info, final_text, notes)` للبحث بكلمة يُضاف في المرحلة 6 عبر Migration (schemaVersion 2).

> **لماذا display_code ليس UNIQUE؟** الجزء العشوائي 6 خانات Hex؛ عند تجميع حالات آلاف الأجهزة لدى المشرف قد يتطابق رمزان ظاهران نادرًا، ولو كان العمود فريدًا لفشل الاستيراد. الهوية الحقيقية هي `id` (UUID).

> **حالة التصدير** لا تُخزَّن كعمود مستقل بل تُشتق: `last_exported_revision == null` → غير مصدّرة، `== revision` → مصدّرة، `< revision` → معدّلة بعد التصدير. هذا يمنع تعارض عمودين.

### `app_settings`
| key TEXT PK | value TEXT | — بيانات غير حساسة فقط (اسم الجهة، رمز المستخدم، الدور، معرف الجهاز المنطقي، آخر رقم تسلسلي...).

### الحالة الظاهرة (Display Status)
تُحسب من ثلاثة مصادر دون تكرار التخزين (`CaseStatusRules` في الكود):
1. `review_state` إن وُجد (لدى المشرف): مستوردة / تحت المراجعة / معتمدة / مرفوضة.
2. وإلا حالة التصدير المشتقة: تم التصدير / تم التعديل بعد التصدير.
3. وإلا `status`: مسودة / مكتملة / جاهزة للإرسال.

## 8) العلاقات (ملخص)

- حذف الحالة = Soft Delete (يضبط `deleted_at` للحالة ومرفقاتها في Transaction واحدة). الحذف النهائي من "المحذوفات" يحذف السجلات والملفات.
- `lookup_items` لا تُحذف فعليًا إن كانت مستخدمة؛ تُعطَّل (`is_active = 0`) حتى لا تنكسر الحالات القديمة.
- عند التصدير تُحمل **النصوص** (label) مع المعرفات، لأن قوائم جهاز المشرف قد تختلف عن قوائم الموظف.

## 9) طريقة تخزين الصور

```
<ApplicationSupport>/attachments/<case_uuid>/EVT-20260925-A72F91_001.jpg
<ApplicationSupport>/attachments/<case_uuid>/thumbs/EVT-20260925-A72F91_001.jpg
```

- مجلد التطبيق الخاص (غير مرئي للمعرض، مستبعد من iCloud/Google Backup التلقائي).
- عند الإضافة: نسخ الصورة من الكاميرا/المعرض إلى المجلد الخاص، ثم حذف النسخة المؤقتة للكاميرا، وإنشاء Thumbnail (عرض ~320px) في Isolate منفصل لعدم تجميد الواجهة.
- ضغط اختياري للصور الكبيرة (مثلًا حد أقصى 2560px وجودة 85%) — إعداد قابل للتغيير.
- **إزالة بيانات EXIF/الموقع من الصور عند التصدير** اختيارًا (الإحداثية محفوظة في الحالة نفسها).
- قاعدة البيانات تخزن المسار النسبي فقط + SHA-256 للتحقق من السلامة عند التصدير/الاستيراد.
- القوائم تعرض الـ Thumbnail فقط؛ الصورة الكاملة تُحمّل عند فتحها.

## 10) صيغة حزمة التصدير (`.casepkg`)

اسم الملف: `<اسم الجهة>_<YYYYMMDD>_<HHmm>.casepkg` مثال: `ينبع_20260925_1930.casepkg`

### الطبقة الداخلية: ZIP منظم
```
manifest.json
cases.json
attachments/
   <case_uuid>/EVT-20260925-A72F91_001.jpg
   <case_uuid>/EVT-20260925-A72F91_002.jpg
```
(المجلد باسم UUID وليس بالرمز الظاهر، لضمان عدم التصادم.)

### الطبقة الخارجية: مغلف مشفّر (من المرحلة 13)
```
[8 bytes]  magic   = "CASEPKG\0"
[2 bytes]  envelope_version = 1
[4 bytes]  header_length
[N bytes]  header.json (غير مشفر، بدون بيانات حساسة):
           { scheme, recipient_key_id, ephemeral_public_key,
             sender_key_id, kdf/salt, nonce_prefix, chunk_size }
[...]      ciphertext = ZIP مشفر بـ AES-256-GCM على شكل قطع (Chunks) 1MB
[64 bytes] توقيع Ed25519 للموظف على (header + ciphertext) — اختياري حسب الإعداد
```
- القارئ يميّز تلقائيًا: يبدأ بـ `PK\x03\x04` → حزمة غير مشفرة (إصدار 1)، يبدأ بـ `CASEPKG` → مغلف مشفر.
- التشفير على شكل قطع يمنع تحميل حزمة من مئات الميغابايت كاملة في الذاكرة. كل قطعة لها nonce مشتق (prefix + counter) و AAD يتضمن رقم القطعة وعلامة "آخر قطعة" لمنع الحذف/إعادة الترتيب.

## 11) صيغة وخطوات الاستيراد

1. اختيار الملف عبر File Picker (أو فتح الملف من WhatsApp/Files بـ "فتح في التطبيق" — تسجيل امتداد `.casepkg`).
2. نسخ الملف إلى مجلد مؤقت خاص بالتطبيق.
3. **فك التشفير** (إن كان مشفرًا) والتحقق من التوقيع ومن أن الحزمة موجهة لمفتاح هذا المشرف.
4. **التحقق من السلامة**: وجود `manifest.json` و`cases.json`، مطابقة SHA-256 لكل ملف، مطابقة الأعداد، دعم `package_format_version`، التحقق من المسارات (منع Zip Slip: رفض `..` والمسارات المطلقة)، حد أقصى للحجم.
5. **التحقق من المحتوى**: كل حالة لها UUID صالح وحقول إلزامية، كل مرفق مذكور موجود فعلًا.
6. **التصنيف** لكل حالة (البند 12) وعرض ملخص الفحص:
   `الدفعة: شرطة ينبع — الحالات 14 — الصور 31 — جديدة 12 — موجودة 2 — أحدث 0 — أخطاء 0`
7. معاينة، ثم **اعتماد الاستيراد** → Transaction واحدة: إدراج الدفعة + الحالات (بحالة `incoming`) + نقل الملفات.
   - الملفات تُنسخ أولًا إلى مجلد مرحلي، وبعد نجاح الـ Commit تُنقل لمكانها النهائي؛ عند الفشل: Rollback وحذف المجلد المرحلي ⇒ لا بيانات نصفية.
8. تسجيل العملية في Audit Log. إعادة استيراد نفس `package_id` تُكتشف وتُعرض كتحذير.

## 12) آلية منع التكرار ومقارنة الإصدارات

المفتاح: **`case_uuid`** (وليس اسم الملف ولا الرمز الظاهر). المقارنة بـ `revision` و`content_hash`:

| الوضع | التصنيف | الإجراء الافتراضي |
|---|---|---|
| UUID غير موجود محليًا | جديدة `new` | استيراد |
| موجود + نفس `content_hash` | مكررة `duplicate` | تجاهل (بدون نسخة مكررة) |
| موجود + `revision` الوارد أكبر | أحدث `newer` | رسالة "توجد نسخة أحدث من هذه الحالة" — والمشرف يختار |
| موجود + `revision` الوارد أصغر | أقدم `older` | تجاهل |
| موجود + نفس `revision` + hash مختلف | تعارض `conflict` | يختار المشرف |
| بيانات غير صالحة / مرفق مفقود | خطأ `error` | لا تُستورد، يظهر السبب |

خيارات المشرف عند `newer`/`conflict`: **مشاهدة الفروقات** (مقارنة حقل بحقل + الصور المضافة/المحذوفة) — **الاحتفاظ بالحالية** — **الاستبدال بالجديدة** — **الاحتفاظ بالنسختين** (النسخة المستبدلة تُحفظ في `case_versions` كسجل إصدارات).

`content_hash` = SHA-256 لتمثيل JSON موحّد (Canonical: مفاتيح مرتبة، بدون الحقول المحلية مثل status/التواريخ المحلية، ومع sha256 المرفقات).

## 13) استراتيجية التشفير (نموذج الحماية المقترح — للاعتماد قبل التنفيذ)

### التهديدات التي نحمي منها
1. وصول شخص غير مخوّل لملف الحزمة (ضياع في محادثة WhatsApp، إعادة توجيه خاطئة، نسخة في Files).
2. التلاعب بمحتوى الحزمة أثناء النقل.
3. ضياع/سرقة جوال الموظف أو المشرف.
4. حزمة مزيفة تُنسب لموظف.

### النموذج المقترح: تشفير هجين بالمفتاح العام (على نمط HPKE/ECIES)

- **المشرف** يولّد عند تفعيل وضع المشرف زوج مفاتيح **X25519** (للتشفير) + **Ed25519** (اختياري للتوقيع). المفتاح الخاص لا يغادر جهازه أبدًا (Keychain/Keystore).
- **الموظف** يستلم **المفتاح العام** للمشرف مرة واحدة فقط عبر **QR حضوري** (أو نص يُلصق) ويتحقق من **البصمة** (Fingerprint قصيرة من 12 حرفًا) مع المشرف.
- عند كل تصدير:
  1. توليد زوج مفاتيح مؤقت (Ephemeral) X25519.
  2. `shared = X25519(ephemeral_private, supervisor_public)`.
  3. `key = HKDF-SHA256(shared, salt = package_id, info = "casepkg-v1")` → مفتاح AES-256.
  4. تشفير ZIP بـ **AES-256-GCM** على شكل قطع، مع ربط الـ header كـ AAD.
  5. المفتاح المؤقت الخاص يُمسح فورًا؛ الحزمة تحتوي فقط المفتاح العام المؤقت.
- **النتيجة**: الملف لا يحمل أي مفتاح يفتحه؛ ولا يُرسل أي مفتاح معه؛ ولا يستطيع فتحه إلا جهاز المشرف. حتى جهاز الموظف نفسه لا يستطيع فك حزمه بعد إنشائها (يحتفظ ببياناته الأصلية في قاعدته).
- **التوقيع (اختياري موصى به)**: الموظف يولّد زوج Ed25519، ويسجّل المشرف مفتاحه العام حضوريًا (QR). المشرف يعرض عند الاستيراد: "موقّعة من: U-117 ✓" أو تحذير "مرسل غير معروف".
- **عدة مشرفين**: يمكن تشفير مفتاح الحزمة لأكثر من مستلم (مفتاح المحتوى يُغلّف لكل مفتاح عام) — مستقبلًا.

### لماذا لا ZIP Password؟
تشفير ZipCrypto ضعيف، و AES-ZIP يعتمد على كلمة مرور مشتركة تُرسل عادة بنفس القناة. النموذج أعلاه لا يحتاج أي كلمة مرور مشتركة.

### بديل احتياطي (Fallback): عبارة مرور للجهة
إن تعذّر توزيع المفاتيح حضوريًا: عبارة مرور طويلة تُسلَّم خارج WhatsApp، ويُشتق منها المفتاح بـ **Argon2id** (ملح عشوائي لكل حزمة داخل الـ header) ثم AES-256-GCM. أضعف من النموذج الأساسي لأنها سر مشترك، لذلك تُستخدم فقط عند الحاجة.

### تشفير البيانات على الجهاز
- قاعدة البيانات بـ **SQLCipher** بمفتاح عشوائي 256-bit يُحفظ في Secure Storage.
- الصور في مجلد التطبيق الخاص تستفيد من تشفير النظام (iOS Data Protection `Complete Until First User Authentication`، Android File-Based Encryption). تشفير كل صورة بشكل مستقل ممكن لاحقًا عند الطلب (كلفة أداء).

### النسخ الاحتياطي
مشفرة بمفتاح مشتق من **كلمة مرور نسخ احتياطي** يختارها المستخدم (Argon2id + AES-256-GCM)، لأن مفاتيح Keystore لا تنتقل لجهاز جديد. التطبيق يوضح: "إذا نسيت كلمة المرور لا يمكن استعادة النسخة".

## 14) إدارة المفاتيح (Key Management)

| المفتاح | أين يُولَّد | أين يُحفظ | هل يغادر الجهاز؟ |
|---|---|---|---|
| مفتاح SQLCipher | الجهاز (CSPRNG) | Secure Storage | لا |
| X25519 خاص للمشرف | جهاز المشرف | Secure Storage | لا، أبدًا |
| X25519 عام للمشرف | جهاز المشرف | app_settings لدى الموظف | نعم عبر QR حضوري فقط |
| Ed25519 خاص للموظف | جهاز الموظف | Secure Storage | لا |
| مفتاح الحزمة (AES) | لكل حزمة، مشتق مؤقتًا | الذاكرة فقط ثم يُمسح | لا |
| PIN | — | يُخزَّن **Hash** فقط (Argon2id + Salt) في Secure Storage | لا |
| كلمة مرور النسخة الاحتياطية | المستخدم | لا تُخزَّن | لا |

- **تدوير المفاتيح**: المشرف يستطيع إنشاء زوج جديد؛ يحتفظ بالقديم للقراءة فقط لفك الحزم القديمة، و`recipient_key_id` في header يحدد المفتاح المطلوب.
- **فقدان جهاز المشرف**: يُولَّد زوج جديد ويُوزَّع المفتاح العام الجديد على الموظفين؛ الحزم غير المستوردة المشفرة بالقديم تحتاج إعادة تصدير من الموظفين (التطبيق يدعم "إعادة تصدير").
- **نسخ المفتاح الخاص للمشرف احتياطيًا** (اختياري): يُصدَّر مشفرًا بكلمة مرور قوية (Argon2id) — يُقرر عند الاعتماد.
- لا توجد أي أسرار Hardcoded في الكود.

## سجل التنفيذ

### المرحلة 1 — المشروع والواجهة الأساسية ✅
- مشروع Flutter (Android + iOS) باسم `field_cases`، اسم التطبيق الظاهر "الحالات الميدانية".
- العربية فقط + RTL، ثيم Material 3 بأزرار كبيرة وبطاقات.
- شريط تنقل سفلي (الرئيسية / الحالات / الإعدادات) + زر عائم "حالة جديدة" أسفل الوسط.
- الرئيسية: ملخص اليوم (الجهة، التاريخ، الدور، عدد حالات اليوم) + بطاقات الإجراءات؛ الاستيراد والدفعات الواردة تظهر للمشرف فقط.
- الإعدادات: تعديل اسم الجهة ورمز المستخدم، عرض الدور.
- اختبار آلي يمنع إضافة أي حزمة شبكة/سحابة/تحليلات، ويتحقق أن Manifest الإصدار لا يطلب إذن INTERNET.

### المرحلة 2 — قاعدة البيانات المحلية ✅
- Drift/SQLite: الجداول الـ 13 الموثقة أعلاه مع الفهارس والمفاتيح الأجنبية (`PRAGMA foreign_keys = ON`).
- البيانات الأولية: أنواع الحالات السبعة، محافظات منطقة المدينة المنورة، مصادر البلاغ، الجهات، والحقول الديناميكية لكل نوع — بمعرفات ثابتة، ولا تُكتب فوق تعديلات المستخدم.
- `CaseIdGenerator`: UUID v4 + الرمز الظاهر `EVT-YYYYMMDD-XXXXXX` + أسماء المرفقات `..._001.jpg`.
- `SettingsRepository` (معرف الجهاز المنطقي، الرقم التسلسلي داخل Transaction، الدور)، `LookupRepository`، `AuditLogger`، `CaseStatusRules`.
- 26 اختبارًا آليًا ناجحًا (`flutter test`).


### المرحلة 3 — إنشاء وتعديل الحالات ✅
- **النموذج المتدرج** (4 خطوات مع شريط تقدم): النوع ← الأساسيات ← التفاصيل ← المراجعة والحفظ.
  - النوع: شبكة أزرار كبيرة، والاختيار ينقل تلقائيًا للخطوة التالية.
  - الأساسيات: التاريخ والوقت (افتراضيًا الآن)، مصدر البلاغ، المحافظة، المركز (مفلتر حسب المحافظة)، الموقع، وصف الموقع.
  - التفاصيل: الحقول الخاصة بالنوع من `case_type_fields`، معلومات الحالة، الإجراء المتخذ، الإصابات/الوفيات بعداد، الأضرار ووصفها، الجهات المباشرة، ملاحظات.
  - المراجعة: ملخص البيانات، والأخطاء مع زر "تعديل" يعيد للخطوة المعنية؛ "حفظ كمسودة" أو "حفظ الحالة".
  - عند الإغلاق مع بيانات غير محفوظة يُطلب تأكيد.
- **قواعد التحقق** (`CaseFormValidator`): المسودة تحتاج نوع الحالة فقط؛ الحالة المكتملة تحتاج المحافظة، والمركز أو الموقع، ومصدر البلاغ، والحقول الإلزامية، ووصف الأضرار إن وُجدت؛ ولا يُقبل وقت في المستقبل.
- **بصمة المحتوى** (`CaseContentHasher`): SHA-256 لتمثيل JSON موحّد. `revision` لا يرتفع إلا إذا تغيّر المحتوى فعلًا، فتتحول الحالة المصدّرة تلقائيًا إلى "تم التعديل بعد التصدير"، وتغيير المرحلة وحده (مثل "جاهزة للإرسال") لا يرفعه.
- **المستودع** (`CasesRepository`): إنشاء/تعديل داخل Transaction واحدة تشمل الرقم التسلسلي والجهات وسجل العمليات؛ فشل الإنشاء يلغي حجز الرقم التسلسلي. الحالات المستوردة (لها `review_state`) مرفوضة للتعديل.
- **تفاصيل الحالة**: عرض كامل مع الشارة، زر "تعديل"/"إكمال المسودة"، و"جاهزة للإرسال" للحالة المكتملة.
- **الحالات السابقة (نسخة أولية)**: أحدث 100 حالة مجمعة باليوم (اليوم/أمس/التاريخ) مع الوقت والنوع والمكان والشارة. التصفية والتحميل التدريجي في المرحلة 6.
- **إدارة القوائم** من الإعدادات: أنواع الحالات، المحافظات، المراكز (مرتبطة بمحافظة)، مصادر البلاغ، الجهات — إضافة، إعادة تسمية، تفعيل/تعطيل (بلا حذف نهائي). وإضافة إعداد "رمز الجهة".
- لا تغيير على مخطط قاعدة البيانات في هذه المرحلة (schemaVersion ما زال 1).
- 48 اختبارًا آليًا ناجحًا. لقطات الشاشات في `docs/screenshots/`.

### المرحلة 4 — الموقع والصور ✅
- **خطوة جديدة "الموقع والصور"** في النموذج (أصبح 5 خطوات).
- **الإحداثيات**: زر "التقاط الموقع الحالي" من GPS الجهاز مباشرة (`forceLocationManager` على Android بدل خدمات Google)، مع عرض الدقة التقريبية؛ نسخ، فتح في تطبيق الخرائط (`geo:` على Android و`maps:` على iOS)، إدخال/تعديل يدوي يقبل الأرقام العربية والفاصلة العربية مع التحقق من النطاق، وإزالة. رسائل واضحة عند إيقاف خدمة الموقع أو رفض الإذن مع زر لفتح الإعدادات.
- **الصور**: الكاميرا، أو عدة صور من المعرض. ضغط أصلي في النظام (حد 2560px وجودة 85%)، وبدون قراءة بيانات EXIF الكاملة.
  - الصورة تُنسخ أولًا إلى منطقة انتظار خاصة (`staging`) وتُحذف النسخة المؤقتة للكاميرا/المعرض، ثم تُحسب بصمتها SHA-256 وتُنشأ مصغرة 320px في Isolate منفصل.
  - عند الحفظ تُنقل إلى `attachments/<case_uuid>/EVT-..._001.jpg` داخل نفس عملية الحفظ؛ وإذا فشل الحفظ تعود لمنطقة الانتظار (لا ملفات يتيمة ولا سجلات بلا ملفات).
  - الترقيم يشمل الصور المحذوفة فلا يتكرر اسم ملف. حذف صورة من حالة محفوظة = حذف مرن (يبقى الملف حتى "المحذوفات").
  - بصمات الصور جزء من بصمة المحتوى: إضافة/حذف صورة يرفع `revision`.
  - الخروج دون حفظ يحذف الصور غير المحفوظة، ومنطقة الانتظار تُنظف عند تشغيل التطبيق.
- **العرض**: شبكة مصغرات في النموذج وفي تفاصيل الحالة، عارض بالحجم الكامل مع التكبير والتنقل، وعدد الصور في قائمة الحالات (استعلام فرعي، دون تحميل الصور).
- **حماية الخصوصية في المنصة**:
  - Android: إزالة إذن `INTERNET` صراحةً من نسخة الإصدار (`tools:node="remove"`)، وتعطيل النسخ الاحتياطي السحابي والنقل التلقائي (`allowBackup=false` + `data_extraction_rules`).
  - iOS: نصوص عربية لأذونات الموقع والكاميرا والمعرض توضح أن البيانات لا تغادر الجهاز.
  - ملاحظة: استبعاد مجلد التطبيق من نسخ iCloud على iOS يُنفذ في المرحلة 13 (يتطلب كودًا أصليًا بسيطًا).
- **فحص العمل دون إنترنت** أصبح أدق: يمنع حزم الشبكة المباشرة، ويمنع أي SDK سحابي/تحليلات في كامل شجرة الاعتماديات، ويفحص كود التطبيق نفسه بحثًا عن أي اتصال شبكي. (حزمة `http` تظهر تبعيةً غير مباشرة لنسخة الويب من `image_picker` ولا تُستخدم على الجوال.)
- لا تغيير على مخطط قاعدة البيانات (جدول `attachments` كان مصممًا لذلك منذ المرحلة 2).
- 66 اختبارًا آليًا ناجحًا.

### المرحلة 5 — الصياغة الآلية والمعاينة والمشاركة ✅
- **محرك القوالب** (`TemplateEngine`) بصيغة قريبة من Mustache ومتغيرات عربية:
  - `{{الوقت}}` استبدال، `{{#وجود_حريق}}…{{/وجود_حريق}}` يظهر إذا وُجدت القيمة، `{{^…}}…{{/…}}` إذا كانت فارغة، مع دعم التداخل.
  - تنظيف تلقائي للنص الناتج (مسافات مكررة، فواصل متتالية، أقواس فارغة) حتى يبقى سليمًا مع الحقول الفارغة.
  - تحقق من بنية القالب ومن المتغيرات غير المعروفة.
- **المتغيرات** (`CaseTemplateVariables`): كل حقول الحالة، والحقول الخاصة بالنوع بعنوانها (مثل `{{حالة_الجسم}}`)، وعبارات جاهزة تراعي قواعد العدد في العربية:
  - `{{عبارة_الإصابات_والوفيات}}`: "دون تسجيل إصابات أو وفيات" / "ونتج عن ذلك إصابتان وحالة وفاة واحدة".
  - `{{الجهات}}`: "الدفاع المدني وإدارة الأسلحة والمتفجرات" بترتيب القائمة.
  - `{{عبارة_الموقع}}`: الموقع كما كُتب، أو "في مركز…"، أو "بمحافظة…".
- **القوالب الافتراضية**: جسم صلب، شظايا، طائرة مسيرة، حريق، وقالب عام لبقية الأنواع. الناتج للمثال المعتمد في المتطلبات (البند 9) مطابق حرفيًا ومغطى باختبار.
- **قاعدة البيانات**: `schemaVersion = 2` — لا تغيير في الجداول؛ Migration تضيف القوالب الافتراضية للقواعد المنشأة بالإصدار 1 (جدول `text_templates` مصمم منذ المرحلة 2). عُدّلت خيارات "حالة الجسم" و"حالة الطائرة" لتُقرأ صحيحة داخل الجملة.
- **شاشة "معاينة الحالة"** (الخطوة 5، بدل المراجعة): النص المولد قابل للتعديل، شارة "معدّل يدويًا"، نسخ النص، مشاركة (النص فقط أو النص والصور)، وإعادة الصياغة من البيانات (بتأكيد إذا كان النص معدلًا)، ثم البيانات والإحداثيات والصور والأخطاء.
  - النص يُعاد توليده تلقائيًا عند فتح المعاينة ما لم يعدله المستخدم، ويُحفظ مع الحالة دائمًا حتى لو حُفظت مسودة دون فتح المعاينة.
- **تفاصيل الحالة**: بطاقة نص الحالة في الأعلى مع "نسخ النص" و"مشاركة" للمشاركة العاجلة.
- **المشاركة**: عبر قائمة المشاركة في النظام (`share_plus`) — المستخدم يختار WhatsApp أو غيره بنفسه، دون أي API.
- **إدارة القوالب** من الإعدادات: قائمة القوالب، إضافة قالب خاص لنوع ليس له قالب، ومحرر فيه إدراج المتغيرات بضغطة، والتحقق، ومعاينة فورية ببيانات مثال، واستعادة القالب الافتراضي.
- 85 اختبارًا آليًا ناجحًا.

### المرحلة 6 — الحالات السابقة والبحث والتصفية ✅
- **البحث النصي** بجدول SQLite FTS5 (`cases_fts`) بمقسّم **trigram**: يطابق أي جزء من الكلمة (3 أحرف فأكثر)، فيجد "المتفجرات" داخل "والمتفجرات" و"الرايس" داخل "بالرايس". الكلمات الأقصر من 3 أحرف يُبحث عنها بمسح نصي (LIKE).
  - **توحيد النص العربي** (`ArabicText.normalize`) للفهرس والاستعلام: إزالة التشكيل والتطويل، أ/إ/آ ← ا، ى/ئ ← ي، ؤ ← و، ة ← ه، الأرقام العربية ← إنجليزية. فيجد "إدارة" عند كتابة "اداره".
  - يشمل: رقم الحالة وجزءًا منه، الرقم التسلسلي، النوع، المحافظة، المركز، مصدر البلاغ، الجهات، الموقع، وصفه، المعلومات، الإجراء، الأضرار، الملاحظات، نص الحالة، المدخل.
  - كل كلمات البحث يجب أن تتطابق (AND)، والرموز الخاصة تُعامل حرفيًا.
  - الفهرس يُحدَّث داخل نفس عملية الحفظ، ويُعاد بناؤه عند إعادة تسمية عنصر في القوائم.
- **الفلاتر**: اليوم، هذا الأسبوع (يبدأ الأحد)، غير مصدرة، مصدرة، معدلة بعد التصدير، ومن "الفلاتر": نوع الحالة، المحافظة، مصدر البلاغ، فترة زمنية (من/إلى شاملة اليومين). يظهر عدد النتائج وزر "مسح الفلاتر".
- **التحميل التدريجي**: 30 حالة لكل صفحة بمؤشر (Keyset Pagination على وقت البلاغ + المعرف) بدل OFFSET، فتبقى الصفحات المتأخرة بسرعة الأولى. القائمة تتحدث تلقائيًا عند أي تغيير في الحالات أو صورها، ويمكن السحب للتحديث.
- **الأداء المقيس في الاختبار** (3000 حالة): 21 صفحة متتالية في نحو 50 مللي ثانية، والبحث النصي مع العد في نحو 5 مللي ثانية.
- زر "البحث" في الرئيسية يفتح نفس الشاشة مع تفعيل حقل البحث مباشرة.
- **قاعدة البيانات**: `schemaVersion = 3` — إضافة جدول البحث الافتراضي `cases_fts` فقط (بيانات مشتقة يمكن إعادة بنائها)، والـ Migration تبنيه من الحالات الموجودة. لا تغيير على الجداول الأساسية.
- 104 اختبارات آلية ناجحة.

### المراحل 7 و8 و9 — التصدير الفردي والجماعي وحزمة `.casepkg` ✅
- **طرق التصدير**:
  - حالة واحدة: زر التصدير أعلى شاشة تفاصيل الحالة.
  - اختيار يدوي: قائمة الحالات في وضع التحديد (مع البحث والفلاتر، و"تحديد الكل") ثم "تصدير المحدد (n)".
  - جميع غير المصدرة: تشمل المعدلة بعد آخر تصدير، والمسودات اختيارية (مستبعدة افتراضيًا). لا تشمل الحالات المستوردة لدى المشرف (لها التصدير الشامل في المرحلة 10).
  - فترة زمنية: من تاريخ إلى تاريخ (شاملة اليومين).
- **خطوات الواجهة**: ملخص وتأكيد (عدد الحالات والصور والحجم التقريبي) ← إنشاء الحزمة ← "مشاركة الملف" عبر قائمة المشاركة (WhatsApp أو "حفظ في الملفات").
- **كاتب الحزمة** (`CasePackageWriter`) وفق الصيغة في البند 10:
  - `manifest.json` (package_id، التاريخ UTC والمحلي، إصدار التطبيق، المصدر: معرف الجهاز المنطقي واسم/رمز الجهة والمدخل، النطاق، الأعداد، قائمة الملفات ببصماتها وأحجامها، وبصمة الحزمة `content_sha256`).
  - `cases.json` بكل حقول الحالة، والقوائم منقولة بالرمز والاسم معًا، والمرفقات بمساراتها وبصماتها.
  - `attachments/<case_uuid>/EVT-..._001.jpg`: الصور تُضاف بالبث من القرص دون ضغط إضافي، وتُعاد حساب بصمتها ومقارنتها بالمخزن قبل الإضافة.
  - الكتابة لملف مؤقت ثم إعادة تسمية: لا يبقى ملف ناقص عند أي خطأ.
- **قارئ الحزمة** (`CasePackageReader`) — جاهز للاستيراد في المرحلة 11: يميز الحزمة المشفرة، يرفض الإصدارات الأحدث برسالة واضحة، يمنع المسارات غير الآمنة (Zip Slip)، ويتحقق من كل ملف (وجود، حجم، بصمة)، ومن بصمة الحزمة، والأعداد، وعدم تكرار الحالات، وعدم وجود ملفات غير مذكورة.
- **بعد التصدير** في Transaction واحدة: تسجيل الدفعة في `export_batches` و`export_batch_items`، وتعليم كل حالة بالمراجعة التي صُدّرت فعلًا (`last_exported_revision`)، وتسجيل العملية في Audit Log. أي تعديل لاحق يجعلها "معدلة بعد التصدير" تلقائيًا.
- **اسم الملف**: `<اسم الجهة>_<YYYYMMDD>_<HHmm>.casepkg` مع إزالة الأحرف غير الصالحة؛ يُعرض في الواجهة بعزل اتجاه الجزء اللاتيني ليُقرأ صحيحًا.
- ملفات التصدير في مجلد مؤقت خاص بالتطبيق وتُحذف عند التشغيل التالي.
- `AppInfo.version` يُكتب في الحزمة، واختبار يتحقق من تطابقه مع `pubspec.yaml`.
- لا تغيير على مخطط قاعدة البيانات (جداول `export_batches` مصممة منذ المرحلة 2).
- 119 اختبارًا آليًا ناجحًا، منها: بناء الحزمة ثم قراءتها، ورفض الحزم المعدلة أو الناقصة أو غير الآمنة.
